# ZeroFrame Backend

ZeroFrame은 경북대학교 컴퓨터학부 학생이 과방이나 실습실에 가기 전에 빈자리를 확인하는 서비스입니다. 이 저장소는 **실습실 장치가 확인한 좌석 상태를 학생의 모바일 좌석도에 전달하는 FastAPI 서버**를 위한 공간입니다.

## 로컬에서 실행하기

개발 환경은 Python 3.13과 uv를 사용합니다. uv가 필요한 경우 [공식 설치 안내](https://docs.astral.sh/uv/getting-started/installation/)를 참고하세요.

```sh
git clone https://github.com/KNUCreaterCrew/backend.git
cd backend
uv sync --locked
echo "EDGE_API_KEY=local-dev-key" > .env
uv run uvicorn app.main:app --reload
```

`uv sync --locked`는 저장소의 `uv.lock`에 기록된 버전으로 가상환경을 구성합니다. 서버는 장치 인증 키를 환경 변수 `EDGE_API_KEY`나 `.env` 파일에서 읽으며, 키가 없으면 시작하지 않습니다. `.env`는 저장소에 올리지 않습니다. 위 키는 로컬 확인용 예시이므로 실제 장치에는 따로 만든 키를 씁니다. 서버가 켜지면 브라우저에서 `http://127.0.0.1:8000/health`를 열어 HTTP 200과 다음 응답을 확인할 수 있습니다.

```json
{"status": "ok"}
```

같은 폴더에서 아래 명령을 실행하면 상태 확인, 방 조회, 혼잡도 집계, 장치 보고 반영, 실시간 알림, 혼잡도 기록 테스트를 실행합니다. 테스트는 테스트용 키를 주입하므로 `.env`가 없어도 됩니다.

```sh
uv run python -m pytest
```

PR을 열거나 `main`에 push하면 GitHub Actions가 같은 명령으로 테스트를 실행합니다. 저장소의 `.gitattributes`는 Windows와 WSL 어느 쪽에서 내려받아도 파일 줄바꿈을 LF로 맞춥니다.

## 방 하나의 좌석 현황 조회

서버를 실행한 뒤 `http://127.0.0.1:8000/api/v1/rooms/IT4-101`을 열면 제1실습실의 좌석 배치와 요약을 볼 수 있습니다. 방과 좌석 정보는 두 곳에서 옵니다.

| 정보 | 보관 위치 | 바뀌는 때 |
| --- | --- | --- |
| 방 이름, 좌석 ID·라벨, 배치 좌표, 콘센트·창가 여부 | [배치 설정 파일](app/data/rooms.json) | 사람이 파일을 고치고 서버를 다시 시작할 때 |
| 좌석 상태와 사유, 상태 변경 시각, 마지막 확인 시각, 장치 연결 여부 | 서버 메모리 | 장치 보고와 연결 감시에 따라 |

방금 시작한 서버는 아직 장치 보고를 받지 못했으므로 모든 좌석이 확인 불가입니다.

| 전체 | 빈자리 | 확인 불가 | 혼잡도 | 장치 연결 |
| --- | --- | --- | --- | --- |
| 4석 | 0석 | 4석 | `HIGH` | `false` |

각 좌석은 `UNKNOWN`·`EDGE_OFFLINE`이고 마지막 확인 시각은 `null`, 상태 변경 시각은 서버 시작 시각입니다. 네 좌석이 각각 빈자리·사용 중·짐 있음·확인 불가인 예시는 [테스트](tests/test_rooms.py)에서 메모리 상태를 바꿔 재현합니다. 등록되지 않은 방 ID로 조회하면 HTTP 404를 반환합니다.

### 요청을 따라 코드 읽기

`app/main.py`의 `create_app()`이 FastAPI 앱을 만들고 라우터를 등록합니다. 앱이 시작될 때(lifespan) [배치 설정 파일](app/data/rooms.json)을 읽어 방 저장소를 만들고 `app.state`에 둡니다. 방 조회 요청 한 건은 아래 순서로 처리됩니다.

| 순서 | 코드 | 맡은 일 |
| --- | --- | --- |
| 1 | [라우터](app/routers/rooms.py) | URL에서 방 ID를 받고, [의존성](app/dependencies.py)으로 저장소를 주입받아 서비스를 호출합니다. 방을 찾지 못하면 HTTP 404로 응답합니다. |
| 2 | [서비스](app/services/rooms.py) → [저장소](app/repositories/rooms.py) | 서비스가 방 ID로 조회하면 저장소가 방의 배치와 메모리의 최신 상태([내부 모델](app/models/rooms.py))를 함께 돌려줍니다. |
| 3 | [서비스](app/services/rooms.py) | 좌석마다 배치와 상태를 합친 뒤 `EMPTY`와 `UNKNOWN`을 따로 세고 빈자리 비율로 혼잡도를 계산합니다. 목록과 집계를 한 응답에 담습니다. |
| 4 | [응답 스키마](app/schemas/rooms.py) | `RoomSnapshot`은 응답의 필드와 타입을 정의합니다. 내부 모델과 분리돼 있어 저장 방식이 바뀌어도 응답 형식은 유지됩니다. FastAPI가 이 형식으로 JSON을 반환하고 `/docs`에 응답 구조를 표시합니다. |

엔드포인트는 `async def`로 작성합니다. 방 상태는 프로세스 메모리에 있으므로 uvicorn은 워커 1개로 실행합니다. 테스트는 `create_app()`으로 매번 새 앱과 새 저장소를 띄우며, 다른 방 데이터를 넣은 저장소를 주입할 수도 있습니다.

집계 기준을 바꿀 때는 서비스를, 데이터를 읽는 방식을 바꿀 때는 저장소를 살펴보면 됩니다. [공통 연동 명세](https://github.com/KNUCreaterCrew/docs/blob/main/INTERFACES.md)

## 장치의 상태 보고 반영

Vision 장치는 맡은 좌석 전체의 상태를 `POST /api/v1/rooms/{room_id}/seats/status`로 보냅니다. 상태가 바뀌면 바로 보내고, 바뀌지 않아도 10초마다 보냅니다. 요청 형식과 반영 규칙은 [공통 연동 명세](https://github.com/KNUCreaterCrew/docs/blob/main/INTERFACES.md)를 따릅니다. 서버를 켠 뒤 아래 예시 보고를 보내고 방을 다시 조회하면 A1이 사용 중으로 바뀌어 있습니다.

```sh
curl -X POST http://127.0.0.1:8000/api/v1/rooms/IT4-101/seats/status \
  -H 'Content-Type: application/json' -H 'X-Edge-Api-Key: local-dev-key' \
  -d '{"room_id":"IT4-101","timestamp":"2026-11-24T10:15:30+09:00","inference_fps":2.1,"saved_frames_count":0,
       "seats":[{"seat_id":"A-01","status":"OCCUPIED","confidence":null,"last_observed_at":"2026-11-24T10:15:29+09:00"}]}'
```

| 경우 | 응답 | 방 상태 |
| --- | --- | --- |
| 키가 없거나 틀림 | 401 | 그대로 |
| 등록되지 않은 방 | 404 | 그대로 |
| 형식 오류, 등록되지 않은 좌석이 섞임, 경로와 본문의 방 ID가 다름 | 422 | 그대로. 일부 좌석만 바뀌지 않습니다. |
| 정상 보고 | 200, `updated_count`는 status·reason이 바뀐 좌석 수 | 보고에 담긴 좌석만 바뀝니다. |

[서비스](app/services/reports.py)는 방별 잠금 안에서 보고를 검증하고, 저장된 상태와 비교해 바뀐 좌석 목록을 만든 뒤 한꺼번에 저장합니다. 같은 보고가 다시 오면 바뀐 좌석이 없으므로 `updated_count`가 0이고 방의 `version`도 그대로입니다. 새 관측이 없는 하트비트는 마지막 확인 시각을 바꾸지 않습니다. 서버는 보고를 받은 시각(`server_time`)을 방마다 기록하며, 이후 장치 연결 판단에 이 시각을 씁니다.

## 실시간 변경 알림

좌석도를 연 웹은 `ws://127.0.0.1:8000/ws/rooms/IT4-101`에 WebSocket으로 연결해 둡니다. 장치 보고로 그 방의 좌석이나 장치 연결이 바뀌면 서버가 같은 방에 연결된 웹에만 `EDGE_STATUS_CHANGED`, `SEAT_UPDATED` 이벤트를 보냅니다. 바뀐 것이 없는 하트비트나 같은 보고의 재전송에는 아무것도 보내지 않습니다. 이벤트 형식은 [공통 연동 명세](https://github.com/KNUCreaterCrew/docs/blob/main/INTERFACES.md)의 3번을 따릅니다.

| 코드 | 맡은 일 |
| --- | --- |
| [WebSocket 라우터](app/routers/realtime.py) | 연결을 수락하고 방별 목록에 등록합니다. 연결이 끊기면 목록에서 뺍니다. 등록되지 않은 방은 종료 코드 `4404`로 닫습니다. |
| [연결 관리](app/connections.py) | 같은 방의 연결에 이벤트를 동시에 보냅니다. 1초 안에 받지 못하는 연결은 종료 코드 `1013`으로 닫습니다. |
| [이벤트 만들기](app/services/events.py) | 반영 결과를 이벤트로 바꿉니다. 집계는 방 조회와 같은 함수로 계산합니다. |
| [보고 반영](app/services/reports.py) | 상태를 저장한 뒤 방 잠금을 쥔 채로 이벤트를 보냅니다. 그래서 웹은 `version` 순서대로 이벤트를 받습니다. |

웹은 **WebSocket 연결 → 방 조회 → 조회 응답의 `version` 이하 이벤트는 버리기** 순서로 시작합니다. 연결이 끊기면 같은 순서로 다시 시작해 빠진 변경을 복구합니다. 서버는 상태나 사유가 바뀐 좌석만 알리므로, 상태가 그대로인 좌석의 마지막 확인 시각은 웹이 30초마다 방을 다시 조회해 맞춥니다. 연결 목록도 프로세스 메모리에 있으므로 uvicorn은 워커 1개로 실행합니다.

### 알림을 보내는 방식과 그 이유

**알림은 방 잠금을 쥔 채로 보냅니다.** 잠금 밖에서 보내면 앞 변경의 전송이 느린 사이 다음 변경이 먼저 도착할 수 있습니다.

```
보고1 저장(version 1) → 잠금 해제 → 전송 시작 … 느린 연결이라 50ms 걸림
보고2 저장(version 2) → 잠금 해제 → 전송 … 1ms
웹 도착 순서: version 2 "A1 빈자리" → version 1 "A1 사용 중"   ← 화면이 옛 상태로 돌아감
```

잠금 안에서 보내면 보고2는 보고1의 전송이 끝난 뒤에 반영되므로 웹은 항상 version 순서대로 받습니다. [테스트](tests/test_realtime.py)에서 전송을 잠금 밖으로 옮겨 보면 도착 순서가 `[2, 1]`로 바뀌어 실패합니다.

**대신 느린 연결 하나가 방 전체를 붙잡지 않게 합니다.** 잠금을 쥔 채로 보내므로, 신호가 약한 학생 한 명에게 20초가 걸리면 그 20초 동안 같은 방의 장치 보고와 다른 학생의 알림이 모두 멈춥니다. 그래서 [연결 관리](app/connections.py)는 두 가지를 합니다.

| 방법 | 효과 |
| --- | --- |
| 같은 방의 연결에 동시에 보냅니다(`asyncio.gather`). | 학생 수와 상관없이 가장 느린 한 명만큼만 걸립니다. |
| 한 연결에 1초 제한을 두고(`asyncio.timeout`), 넘기면 종료 코드 `1013`으로 닫습니다. | 전송 전체가 1초 안에 끝나므로 잠금도 1초 넘게 붙잡히지 않습니다. |

느린 연결에 이번 알림만 건너뛰고 연결을 유지하면, 그 웹은 놓친 변경을 모른 채 다음 변경부터 받아 화면이 계속 틀립니다. 연결을 닫으면 웹이 다시 연결하고 방 전체를 조회해 스스로 맞춥니다. 연결마다 대기열을 두고 따로 보내는 방법도 있지만, 한 방에 수십 명 규모에서는 제한 시간만으로 충분하다고 판단했습니다.

## 장치 연결 감시

장치가 멈추면 학생 화면에 오래된 빈자리가 남지 않도록, 서버는 켜져 있는 동안 [감시 작업](app/services/edge.py)을 1초마다 돌립니다. 마지막 보고를 받은 뒤 30초가 지난 방은 오프라인으로 바꾸고, 전 좌석을 `UNKNOWN`·`EDGE_OFFLINE`으로 바꿔 `EDGE_STATUS_CHANGED`와 `SEAT_UPDATED`로 알립니다. 장치가 다시 보고하면 보고 반영 경로가 방을 온라인으로 돌리고, 보고에 담긴 상태만 반영합니다. 끊기기 전 상태를 되살리지 않습니다.

| 시각 | 서버 | 웹이 받는 알림 |
| --- | --- | --- |
| 10:15:40 | 하트비트 수신, 수신 시각 기록 | 없음 |
| 10:16:10 | 30초 전이므로 그대로 | 없음 |
| 10:16:11 | 30초 넘음 → 오프라인 전환 | version 2: 장치 끊김, A1 확인 불가 |
| 10:16:12 이후 | 이미 오프라인이므로 건너뜀 | 없음 |
| 10:17:05 | 장치 보고 반영 | version 3: 장치 연결, A1 사용 중 |

### 감시를 이렇게 만든 이유

- **30초는 서버가 보고를 받은 시각으로 잽니다.** 장치 시계는 재시작 직후 틀릴 수 있습니다. 장치의 `timestamp`로 재면, 시계가 5분 뒤로 가 있는 장치는 보고를 보내는 중에도 끊긴 것으로 판정됩니다.
- **판단과 전환을 방 잠금 안에서 합니다.** 보고 반영과 같은 잠금을 쓰므로, 끊김 판단과 새 보고가 동시에 들어와도 한쪽이 끝난 뒤 다른 쪽이 실행됩니다. 현재 시각도 잠금을 잡은 뒤에 읽어, 기다리는 사이 들어온 보고까지 보고 판단합니다. [테스트](tests/test_edge.py)는 두 작업을 동시에 실행해 알림이 version 순서(끊김 → 재연결)대로 나가고 최종 상태가 온라인인지 확인합니다.
- **이미 오프라인인 방은 건너뜁니다.** 같은 끊김 알림이 1초마다 반복되지 않습니다.
- **좌석 전환 규칙은 장치 보고와 같은 함수를 씁니다**(`SeatState.transition`). 확인 불가가 된 좌석의 상태 변경 시각은 전환 시각이 되고 마지막 확인 시각은 유지됩니다. 이미 확인 불가였던 좌석은 사유만 바뀝니다.
- **한 방에서 오류가 나도 감시는 계속됩니다.** 오류를 기록하고 다음 방으로 넘어갑니다. 감시 작업이 멈추면 모든 방의 끊김 표시가 함께 멈추기 때문입니다.
- **테스트는 시계를 주입합니다.** `create_app(clock=..., edge_check_interval=...)`로 서버 시계와 확인 주기를 바꿔, 30초를 기다리지 않고 29.999초와 30초 경계를 검증합니다.

## 혼잡도 기록

학생이 "이 실습실은 보통 언제 한산한지"를 그래프로 볼 수 있도록, 서버는 켜져 있는 동안 **1분마다 방 요약 한 줄**을 SQLite에 남깁니다. 기록 단위와 평균 규칙은 [공통 연동 명세 4절](https://github.com/KNUCreaterCrew/docs/blob/main/INTERFACES.md#4-웹이-혼잡도-통계를-읽습니다)을 따릅니다. 실시간 좌석 상태는 지금처럼 메모리에 두고, SQLite에는 기록만 쌓습니다.

| 열 | 값 |
| --- | --- |
| `room_id`, `recorded_at` | 방 ID, 기록한 분(UTC, `2026-11-24T01:00:00+00:00`). 둘을 합친 값이 기본키입니다. |
| `total_seats`, `available_seats`, `unknown_seats` | 방 조회 응답과 같은 `summarize()`로 계산한 전체·빈자리·확인 불가 좌석 수 |
| `edge_online` | 장치 연결 여부(0/1) |
| `source` | `OBSERVED`(실제 기록) 또는 `SEED`(시연용 예시 기록) |

기록 파일 경로는 환경 변수 `STATS_DB_PATH`로 정하며, 기본값은 실행한 폴더의 `var/stats.sqlite3`입니다. `var/`는 저장소에 올리지 않습니다. 테스트는 임시 파일을 씁니다.

```sh
# 기록을 열어 보기 (sqlite3 CLI가 있다면)
sqlite3 var/stats.sqlite3 "SELECT * FROM room_minutes ORDER BY recorded_at DESC LIMIT 5"
```

### 기록을 이렇게 만든 이유

- **기록에는 사실만 남깁니다.** 장치가 끊긴 분도 `edge_online = 0`, 빈자리 0으로 그대로 남기고, 평균에서 빼는 일은 조회가 맡습니다. 기록 단계에서 거르면 나중에 규칙을 바꿀 때 지난 기록을 되돌릴 수 없습니다. 서버가 꺼져 있던 분은 기록이 없고, 조회는 이것도 '확인할 수 없는 분'으로 봅니다.
- **1초마다 분이 바뀌었는지 확인합니다.** `sleep(60)`을 반복하면 처리 시간만큼 조금씩 밀리다가 어느 분을 통째로 건너뜁니다. [기록 작업](app/services/stats.py)은 마지막으로 기록한 분보다 지금 분이 클 때만 기록하므로 밀리지 않습니다. 장치 연결 감시와 같은 구조라 테스트에서는 주입한 시계만 옮기면 됩니다.
- **디스크 쓰기는 별도 스레드에서 합니다.** 표준 `sqlite3`는 동기 라이브러리라, 이벤트 루프에서 바로 쓰면 그동안 장치 보고와 WebSocket 알림이 멈춥니다. `asyncio.to_thread`로 넘깁니다. `aiosqlite`도 내부에서 스레드를 쓰므로, 1분에 한 번 쓰는 규모에서는 의존성을 늘리지 않았습니다.
- **쓸 때마다 연결을 엽니다.** `sqlite3` 연결은 만든 스레드에서만 쓸 수 있는데(`check_same_thread`), `to_thread`는 매번 같은 스레드를 쓴다는 보장이 없습니다. 연결 하나를 공유하면 "다른 스레드에서 만든 연결" 오류가 납니다.
- **방 상태는 잠금 안에서 읽고, 쓰기는 잠금 밖에서 합니다.** 방 잠금은 장치 보고 반영도 막으므로 숫자만 복사하고 바로 놓습니다.
- **같은 방·같은 분은 한 줄입니다(`INSERT OR IGNORE`).** 서버를 같은 분 안에 다시 켜도 중복되지 않고, 시드가 실제 기록을 덮어쓰지 않습니다.
- **기록이 실패해도 서버는 계속 돕니다.** 오류를 로그에 남기고 다음 분에 다시 시도합니다. 좌석 안내가 통계 때문에 멈추면 안 되기 때문입니다.
- **지우지 않습니다.** 방 하나에 하루 1,440줄, 한 달에 약 4만 줄(수 MB)이라 해커톤 기간에는 정리하지 않습니다.

### 시연용 예시 기록

시연 날에는 실제 기록이 몇 시간치뿐이라 요일·시간대별 평균을 채울 수 없습니다. [시드 스크립트](demo/seed_stats.py)가 어제까지 28일치를 `source = SEED`로 만듭니다.

```sh
uv run python -m demo.seed_stats            # 기본 28일, STATS_DB_PATH 또는 var/stats.sqlite3
uv run python -m demo.seed_stats --days 7
```

평일 10~17시는 붐비고 점심과 주말은 한산하게, 밤(22시~8시)은 장치를 끈 것으로 만들어 그래프의 빈 구간도 시연할 수 있습니다. 오늘은 넣지 않고, 이미 기록이 있는 방·분은 건너뛰며, 몇 번을 돌려도 같은 기록이 나옵니다.

### Render 무료 플랜에 배포할 때

Render 무료 웹 서비스는 디스크가 임시라 **재배포·재시작·스핀다운 때 SQLite 파일이 사라지고**, 영구 디스크도 붙일 수 없습니다. 15분 동안 요청이 없으면 스핀다운되지만, 장치가 10초마다 보고하는 동안에는 깨어 있습니다. [Render 무료 플랜 안내](https://render.com/docs/free)

- 시작 명령에서 시드를 먼저 넣습니다. 시드는 몇 번을 돌려도 같으므로 재배포할 때마다 다시 채워집니다.
  `python -m demo.seed_stats && uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- 실제 기록은 마지막 배포 이후의 것만 남습니다. 시연 당일에는 재배포하지 않습니다.
- 기록을 오래 남기려면 유료 인스턴스로 올리고 영구 디스크를 붙인 뒤, `STATS_DB_PATH`를 디스크 경로(예: `/var/data/stats.sqlite3`)로 지정합니다. 코드는 바꾸지 않아도 됩니다.

## 카메라 없이 시연하기

Vision 장치 없이 예시 보고로 학생의 좌석 안내 흐름을 처음부터 끝까지 재현합니다. [시연 스크립트](demo/__main__.py)가 장치(보고 전송)와 학생의 웹(WebSocket 연결·방 조회)을 함께 흉내 내고, 단계마다 조회 결과와 알림을 대조합니다. 보고에는 좌석 메타데이터만 담깁니다.

```sh
# 터미널 1: 서버를 새로 시작합니다. 이전 상태가 남아 있으면 시연이 첫 단계에서 멈춥니다.
EDGE_API_KEY=local-dev-key uv run uvicorn app.main:app

# 터미널 2: 1분 남짓 걸립니다. 키는 --key, 환경 변수 EDGE_API_KEY, .env 순으로 찾습니다.
uv run python -m demo
```

[시나리오](demo/scenario.py)는 예시 실습실 IT4-101(4석)에서 아래 순서로 진행합니다. 모든 단계가 기대와 일치하면 `7/7 단계가 기대와 일치합니다.`를 출력하고 종료 코드 0으로 끝납니다.

| 시점 | 장치가 하는 일 | 웹이 받는 알림 | 조회 결과 |
| --- | --- | --- | --- |
| 시작 | (보고 전) | 없음 | 빈자리 0 / 전체 4석 · 확인 불가 4석 · 장치 끊김 |
| +0초 | 첫 보고: A1 빈자리, A2 사용 중, B1 짐 있음, B2 가림 | `EDGE_STATUS_CHANGED`, `SEAT_UPDATED` (v1) | 빈자리 1 / 전체 4석 · 확인 불가 1석 · `MODERATE` |
| +10초 | 하트비트 (변화 없음) | 없음 | 그대로 |
| +15초 | A1에 학생이 앉음 | `SEAT_UPDATED` (v2) | 빈자리 0 · `HIGH` |
| +25초 | 하트비트 (A1을 다시 확인) | 없음 | 그대로. A1의 마지막 확인 시각만 바뀜 |
| +56초 | (보고 끊김, 마지막 보고 후 31초) | `EDGE_STATUS_CHANGED`, `SEAT_UPDATED` (v3) | 확인 불가 4석 · 장치 끊김 |
| +70초 | 재연결: A1 사용 중, A2 빈자리, B1 관측 만료, B2 가림 | `EDGE_STATUS_CHANGED`, `SEAT_UPDATED` (v4) | 빈자리 1 · 확인 불가 2석 · `MODERATE` |

[e2e 테스트](tests/test_e2e.py)는 같은 시나리오와 같은 대조 규칙을 가짜 시계로 실행하므로, CI가 이 흐름을 1초 안에 매번 다시 확인합니다. 위 결과는 **예시 입력으로 재현한 것**입니다. Vision 송신기를 실장치에 연결해 확인하면 결과를 따로 기록합니다.

## 학생이 좌석도를 열면

| 상황 | 백엔드가 맡을 일 |
| --- | --- |
| 학생이 제1실습실을 선택합니다. | 방의 좌석 배치와 최근 상태를 함께 반환합니다. 빈자리와 확인 불가 좌석은 따로 집계합니다. |
| 다른 학생이 A1에 앉습니다. | Vision 장치가 보낸 상태를 반영하고, 이 방을 보고 있는 학생들에게 WebSocket으로 변경을 알립니다. |
| 실습실 장치의 연결이 끊깁니다. | 30초 이상 보고가 없으면 해당 방의 좌석을 ‘확인 불가’로 바꿉니다. 연결이 돌아오면 새로 확인된 자리부터 상태를 갱신합니다. |

카메라 영상과 좌석 이미지는 실습실 장치 안에서 처리합니다. 백엔드가 받는 데이터는 방·좌석 ID, 상태, 관측 시각 등의 JSON입니다.

서비스의 기획과 시스템 간 연동 명세는 공통 문서 저장소에서, 카메라 관측과 좌석 판정은 Vision 저장소에서 관리합니다. [공통 문서](https://github.com/KNUCreaterCrew/docs) · [Vision](https://github.com/KNUCreaterCrew/vision)
